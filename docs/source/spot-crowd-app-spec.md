## 1. 概要

### 1.1 目的

ポーカープレイヤーが、自分のハンドの特定の場面（スポット）で「相手ならどんなレンジでどう行動するか」を、他のプレイヤーの回答から集合知として知るためのウェブアプリ。

### 1.2 基本の流れ

1. Hero（投稿者）が自分のハンドヒストリーを登録し、Hero のアクションを 1 つと Villain の席を 1 つ選んでスポットとして投稿する。
2. 回答者は Villain の席に座り、スポットまでのリプレイを見たうえで、13×13 のレンジ表にアクション頻度を塗って回答する。
3. 回答後、回答者全体の集計レンジ、Villain の実際のアクションとハンド（判明している場合）、ハンドヒストリーの全体が見られる。
4. Hero は自分のスポットに集まった回答を同じ形式で確認でき、自分の予想（Hero の予想）も入力できる。

### 1.3 位置づけ

- ソルバーのような均衡解を出すものではなく、人の判断のばらつきを見る「アンケート」に近い道具である。
- 完璧なレンジは求めない。13×13（169 ハンド、スートを区別しない）の近似で扱う。
- 1 投稿につき、回答対象は Hero が指定した 1 スポットの Villain の 1 アクションのみ。

### 1.4 やらないこと（スコープ外）

- チャット、コメント、リアクション、フォローなどの交流機能は一切持たない。
- プレイ中の意思決定支援（RTA）は目的としない。
- ソルバー計算、EV 計算、エクイティ計算は行わない。
- 画像の保存は行わない（OCR 後に破棄）。
- ICM 情報（残り人数、ペイアウト）は扱わない。

## 2. 用語

アプリ内の表示はポーカーの専門用語に統一する。

| 用語 | 意味 |
|---|---|
| Hero | スポットを投稿したプレイヤーの席 |
| Villain | 回答対象の席。回答者はこの席の立場でレンジを入力する。回答画面の席ラベルのみ「Villain（あなた）」と表示する |
| スポット | Hero のアクション直後から、Villain が次にアクションする直前までの局面 |
| レンジ内 / レンジ外 | そのスポットに Villain が持って到達するハンド / 到達しないハンド。塗らないマスはレンジ外 |
| ミックス（混合戦略） | 1 ハンドに対する複数アクションの頻度の組み合わせ（合計 100%、5% 刻み） |
| ブラシ | 塗る際に適用するミックス |
| to call / to act | コールに必要な額 / 次にアクションする席 |
| % pot | コール後のポットに対する割合（計算式は 6.6） |
| ランアウト | オールインでアクションが終わった後、残りのボードを配ること |
| マック | ショーダウンでハンドを見せないこと。ハンド未入力の席はマック扱い |
| 実効スタック | Hero と Villain のスタックの小さいほう（スポット時点） |

## 4. 画面構成と遷移

| 画面 | 主な内容 | 遷移先 |
|---|---|---|
| スポット一覧 | 投稿の一覧、フィルタ、並び替え | 回答 / 集計 / スポット投稿 |
| スポット投稿 | ハンドヒストリー入力、スポット選択、タイトル | 一覧（自分の投稿タブ） |
| 回答（レンジ入力） | リプレイ、レンジ入力 | 集計 |
| 集計 | 集計レンジ、実際のアクション、ハンドヒストリー | 一覧 / 回答（Hero の予想の編集のみ） |
| インフォメーション | 現在の画面の説明（モーダル） | ― |
| アカウント | 利用規約、プライバシーポリシー、ログアウト、アカウント削除（メニュー） | ― |

- 未回答のスポットは回答画面へ、回答済みのスポットと自分の投稿は集計画面へ遷移する。
- 他人のスポットの集計は、回答するまで閲覧できない（サーバー側で強制。7.6）。

### 4.1 共通 UI 方針

- 画面上に説明文を一切表示しない。説明はすべてヘッダーのインフォメーションボタン（ⓘ）から開くモーダルに収める。例外は入力欄のプレースホルダーとエラー表示。操作方法を説明するトーストも出さない（受け付けない入力は無視するか、エラーとして短く表示する）。
- ポーカー用語は専門用語を使う（2 章）。
- スマホ用 UI は PC 版の縮小ではなく、画面構成を変える（各章に記載）。
- ライト / ダークテーマの両方に対応する。
- ヘッダー右上に ⓘ ボタンとアカウントアイコンを置く。

## 5. 機能仕様

### 5.1 スポット一覧

| 項目 | 仕様 |
|---|---|
| タブ | 「すべて」「自分の投稿」 |
| フィルタ | ストリート（すべて / プリフロップ / フロップ / ターン / リバー）。スポットのストリート（Villain の実際のアクションのストリート）で判定 |
| 並び替え | 新着順 / 回答数が多い順 |
| カード表示 | ストリート、ゲーム形式、実効スタック（bb）、タイトル、`Hero {位置} vs Villain {位置}`、回答数、投稿からの経過時間、状態（回答済み / 自分の投稿） |
| 操作 | 「回答する」「結果を見る」「回答を見る」。自分の投稿には「削除」。管理者にはすべての投稿に「削除」 |
| 読み込み | 一覧用の要約（7.1）のみを 20 件ずつ読む。ハンド本体は回答・集計画面で読む |
| スマホ | カードは 1 列。「＋ スポットを投稿」を画面下部に固定 |
| 空状態 | 「投稿なし」「該当スポットなし」の短い表示のみ |

### 5.2 スポット投稿

#### 5.2.1 構成

- PC: 1 画面に「基本設定」「プレイヤーとハンド」「アクション入力」「スポット」を並べる。
- スマホ: 4 ステップ（基本設定 → プレイヤー → アクション → スポット）。上部にステップ表示（タップで移動可）、下部に「戻る / 次へ」、最終ステップは「投稿する」。

#### 5.2.2 画像読み込み（OCR）

- 「T4ハンドヒストリー画像を読み込む」ボタンから、T4 のハンドヒストリー画像を OCR で読み込む。既存の T4watcher の OCR を流用する。
- OCR は端末内（ブラウザ内）で完結させ、画像を外部に送信しない。流用元の実装が外部 API を使っている場合は、本アプリでは端末内処理に置き換える（プライバシーポリシーの記述と一致させるため）。
- 読み取り結果はフォームに反映され、ユーザーが確認・修正してから投稿する。
- 画像は読み取り後ただちに破棄し、保存しない。

#### 5.2.3 基本設定

| 項目 | 仕様 |
|---|---|
| ゲーム形式 | キャッシュゲーム / MTT |
| 人数 | 6max 固定。ポジションは UTG, HJ, CO, BTN, SB, BB |
| SB / BB | bb 単位で入力 |
| アンティ | 任意。bb 単位で全員から徴収 |
| レーキ | キャッシュゲームのみ任意入力（%）。MTT では入力不可。値は保存するが計算には使わない |
| ロック | アクションを 1 つでも入力すると、基本設定・スタック・Hero の席は変更不可。変更するにはアクションを全消去する |

#### 5.2.4 プレイヤーとハンド

- 各席に「スタック（bb）」「ハンド」「Hero（ラジオ）」を持つ。
- ハンドは分かっている席だけ入力する。Hero のハンドは必須。フォールドした席でもハンドが判明していれば入力してよい（見せた場合など）。
- ハンド欄を押したときだけ、カードキーボードを画面下部（スマホのソフトキーボードが出る位置）に表示する。「完了」、キーボード外のタップ、Esc で閉じる。
- 開いたとき、押したハンド欄がキーボードに隠れないよう自動スクロールする。

#### 5.2.5 カードキーボード

配列（4 列 × 4 行、空きマスなし。A と ♠ は縦 2 マス）:

```
7  8  9  [A]
4  5  6  [A]
1  2  3  [♠]
C  0  ⌫  [♠]
```

| キー | 動作 |
|---|---|
| 2〜9 | ランクを入力 |
| A（フリック） | タップで A。押したまま上で K、右で Q、下で J、左で T |
| ♠（フリック） | タップで ♠。上で ♥、右で ♦、下で ♣ |
| 1 → 0 | T（10）を入力 |
| 1 単独、0 単独 | 確定しない。1 のあとに 0 以外のランクを押すとそのランクに置き換わる。1 のあとにスートを押しても確定しない（無視） |
| C | 入力中の席のハンドをクリア |
| ⌫ | 1 文字削除 |

- 入力はランク → スートの順。スート待ちでランクを押すと、直前のランクを置き換える。
- 1 席 2 枚まで。3 枚目以降の入力は無視する。
- 他の席のハンドとボードで使用済みのカードは入力できない（エラートーストで通知。これは操作説明ではなくエラー表示として許容する）。
- フリックは長押し 150ms またはドラッグ開始でポップアップを表示する。上下左右の判定は移動距離 25px 超で行う。ポップアップはキーボード領域からはみ出さないよう位置を補正する。
- 参考元の入力パッドにあった Action キー、表示欄、小数点キーは採用しない。

#### 5.2.6 アクション入力

- 次に行動する席（to act）、ストリート、to call、残りスタックを表示する。
- ボタンはフォールド / チェック / コール（額表示）/ ベット / レイズ。取れないアクションは非活性。
- ベット額・レイズ額（レイズは to 表記）は数値入力。初期値は、to call = 0 のとき「ポットの 50%（min〜max に丸める）」、to call > 0 のとき最小レイズ to。範囲外はエラートーストで拒否する。
- 「1つ戻す」は最後のアクションだけを取り消す。ボードは残す（ストリートが戻っても、そのストリートに再到達したときにボード入力を求めない）。「すべて消す」はアクションとボードの両方を消す。
- ストリートが終わるとボード入力を要求する。ボードの「＋」からカードピッカーで選ぶ（使用済みカードは選択不可）。
- 入力済みのボードカードを押すと、そのカード以降のボードと、そのストリート以降のアクションを削除する。
- ハンド終了時は「{位置} ポット獲得」または「ショーダウン」を表示する。ショーダウンでは、残った各席の入力済みハンドを表示し、未入力はマックとして扱う。
- 判定ロジックは 6 章。

#### 5.2.7 スポット選択とタイトル

- Hero のアクションの候補: Hero のフォールド以外のアクションのうち、その後、Hero が次にアクションするまで（Hero がオールインならハンド終了まで）の間に他の席のアクションがあるもの。
- Villain の候補: その区間でアクションした席（フォールドした席も含む。フォールドの判断を出題できる）。1 人なら自動選択（選択 UI は非活性）、複数なら Hero が選ぶ。
- 停止位置: 選んだ Hero のアクション以降で、Villain が最初にアクションする直前。間に他の席のアクションがあれば、それも含めてリプレイする。Villain が同じ区間で複数回アクションしていても、回答対象は最初の 1 アクションのみ（1.3）。
- タイトル: 必須、40 文字まで。
- 投稿時に、停止位置から次の派生メタを計算して保存する（7.1）: スポットのストリート、Villain の合法アクションのキー、レイズ（ベット）の min / max、ポット基準、実効スタック。

#### 5.2.8 投稿時のバリデーション

クライアントとサーバーの両方で行う。

- Hero のハンドが 2 枚入力されている。
- 途中入力（1 枚のみ、スート未確定）のハンドがない。
- ハンドが最後まで入力されている（ポット獲得またはショーダウンに到達）。
- アクション列が 6 章のロジックで再生可能である（サーバー側は再生して派生メタを再計算し、クライアントの値と一致しない場合は拒否する）。
- スポットと Villain が選択されている。
- タイトルが空でない。
- 投稿者のその日（UTC）の投稿数が上限（5 件）未満である（サーバー側のみ）。

エラーは一覧で表示する（スマホは下部バー内）。投稿後は一覧の「自分の投稿」タブへ戻る。

### 5.3 回答（レンジ入力）

#### 5.3.1 構成

- PC: 左にリプレイ、右にレンジ入力。
- スマホ: 上部固定のタブ「リプレイ / レンジ」。
  - リプレイタブ: テーブル、再生コントロール、ハンドヒストリー（折りたたみ）。下部に「レンジ入力」ボタン。
  - レンジタブ: 上部固定パネルに「ブラシパネル」と「サイズ（畳んだ 1 行）」を置き、その下にレンジ表。下部に集計バーと「回答する」を固定。レンジ表の下には操作要素を置かない（レンジ表は `touch-action: none` のため、表の下に置いた要素へスクロールしにくい）。

#### 5.3.2 リプレイ

- 画面を開くと、スポットの停止位置まで自動再生する（1 手 650ms。視差効果を減らす設定の端末では即座に停止位置を表示）。
- 操作: 最初から / 1手戻る / 再生・一時停止 / 1手進む（停止位置より先には進めない）。
- テーブルは Villain の席を手前（下中央）に回転して表示する。Hero の席は「Hero」、Villain の席は「Villain（あなた）」と表示し、Villain の席は青枠で強調する。
- Hero のハンドは裏向きで表示し、回答後に公開する（Hero のハンドと knownCards は、回答済みのユーザーにだけサーバーが返す。7.6）。
- 表示要素: ポット、ボード（到達ストリート分）、各席のスタック・直前のアクション・ベット額のチップ、to act の強調。

#### 5.3.3 ブラシとミックス

- 上部にアクションのタイル（フォールド / コール / レイズ、または チェック / ベット、または チェック / レイズ。6.3 の合法アクションに従う）と、頻度のミックスバーを置く。
- タイルを押すと、そのアクション 100% のブラシになる。
- ミックスバーの境界ハンドルをドラッグすると、隣接アクションの頻度を調整できる。刻みは 5%。ハンドルはキーボードの左右キーでも操作できる。
- 複数のハンドルが同じ位置に重なっている場合、ドラッグ開始時に「その方向へ動ける」ハンドルを掴む（右へドラッグなら左側の境界、左へドラッグなら右側の境界）。動ける方向が判定できるまで（移動 6px 未満）は掴むハンドルを確定しない。
- 常にブラシの合計は 100%。
- タイルにはアクション名、頻度、コール額またはレイズサイズを表示する。

#### 5.3.4 塗り

- マスをタップ、またはなぞるとブラシのミックスで塗る。なぞった一連の操作は 1 回として扱う。
- ブラシと同じミックスのマスから操作を始めた場合は消去として動作する（なぞった範囲も消去）。
- 塗らないマスはレンジ外。
- マスの表示は、頻度に応じて左からアクション色を並べる（フォールド → チェック → コール → レイズの順）。
- スポイト: マスを 480ms 長押しすると、塗りを取り消したうえで、そのマスのミックスをブラシに読み込む。レンジ外のマスでは「レンジ外」とトースト表示のみ。

#### 5.3.5 道具

- ブラシ / 消しゴム（レンジ外に戻す）の切り替え。
- 元に戻す / やり直す（最大 100 手）。
- クリア（全マスをレンジ外。元に戻す対象）。
- そのスポットで取れないアクションは、非活性ボタンとして表示する（スマホでは非表示）。

#### 5.3.6 サイズ

- レイズ（ベット）は 1 サイズのみ。
- 通常は「レイズサイズ {bb} {% pot}」の 1 行に畳み、開くとプリセット・入力欄・ゲージを表示する。スマホでは上部固定パネル内に置く（5.3.1）。
- プリセット: 33% / 50% / 75% / 125% / オールイン。初期値は 50%。
- 入力欄（bb、0.1 刻み）とゲージ（min〜max）で任意に調整できる。
- min / max と範囲外の警告を表示する。

#### 5.3.7 集計バー

- 1326 combos に対する各アクションとレンジ外の比率を、積み上げバーと数値で常時表示する。コンボ数はペア 6、スーテッド 4、オフスート 12 とし、ボードとのカード除外は行わない。

#### 5.3.8 送信

- 少なくとも 1 マス塗っていること。
- レイズ（ベット）を含むマスがある場合は、サイズが範囲内であること。
- 回答は 1 ユーザー 1 スポット 1 回。送信後は編集できない（集計を見たあとの答え直しを防ぐため）。送信ボタンの確認ダイアログで「送信後は変更できない」旨を表示する。
- 自分の投稿に対する入力は「Hero の予想」として保存し、全体の集計には含めない。Hero の予想は何度でも上書きできる。
- サーバー側の検証（7.6）: 投稿者本人の回答は拒否（Hero の予想は別の経路）、既存回答があれば拒否、paint のキーが 169 ラベルの範囲内、各マスのミックスのキーが派生メタの合法キーの範囲内、各マスの合計が 20（=100%）、サイズが min〜max。

### 5.4 集計

#### 5.4.1 構成

- PC: 左にハンドヒストリーの再生、右に集計。
- スマホ: 上部固定のタブ「集計 / ハンドヒストリー」。

#### 5.4.2 集計レンジ

- タブ: 「全体（N人）」「自分」「Hero の予想」。自分の投稿では「全体」「Hero の予想」。
- 全体表示のマス:
  - 色の割合: そのハンドをレンジ内とした回答者のミックスの平均（各アクションの合計頻度 ÷ レンジ内人数）。
  - 濃さ: レンジ内とした回答者の割合（不透明度 0.3〜1.0）。0 人は無色。
- 自分 / Hero の予想の表示: そのミックスをそのまま表示する。
- 白枠: Villain の実際のハンド（判明している場合のみ）。
- マスを選ぶと、内訳を表示する（全体: レンジ内 n / N 人と各アクションの割合と人数、自分の回答のミックス）。
- 上部に 1326 combos 基準の比率を積み上げバーと数値で表示する。全体表示の比率は次で定義する。
  - アクション k の比率 = Σ_マス combos(マス) × (レンジ内人数 / N) × 平均頻度 k ÷ 1326
  - レンジ外の比率 = Σ_マス combos(マス) × (1 − レンジ内人数 / N) ÷ 1326
- 回答数が 1 件でも表示する（回答数を併記して信頼度の目安とする）。
- 回答がない場合は「回答なし」、Hero の予想がない場合は「予想なし」（自分の投稿では「予想を入力」ボタン）。

#### 5.4.3 実際のアクション

- Villain の実際のアクション（額を含む）と、ハンド（判明時はカード表示、未判明は「マック」または「ハンド不明」）を表示する。

#### 5.4.4 ハンドヒストリー

- ハンドの最後まで再生でき、終了時は Hero のハンドと判明しているハンドを公開する。
- ログ上で Hero のスポットのアクションに「出題」タグ、Villain の実際のアクションを強調表示する。

#### 5.4.5 操作

- 自分の投稿では「予想を編集」で回答画面へ戻る。他人の投稿では回答の編集はできない（5.3.8）。
- 自分の投稿は「削除」できる。管理者はすべての投稿を「削除」できる。

### 5.5 削除

- Hero は自分の投稿を削除できる。管理者はすべての投稿を削除できる。確認ダイアログを表示する。
- 投稿を削除すると、集まった回答と集計データもサーバー側で削除する（クライアントは投稿の削除だけを要求する）。
- 回答者が自分の回答を削除する手段は持たない。回答が消えるのは投稿削除とアカウント削除のときだけ。

### 5.6 インフォメーション

- ヘッダーの ⓘ から、表示中の画面（一覧 / スポット投稿 / レンジ入力 / 集計）の説明をモーダルで表示する。
- 画面上に出していた説明文、操作方法、記号の意味（色の割合、濃さ、白枠など）はすべてここに集約する。内容は 10 章。

## 6. ポーカーロジック

### 6.1 アクション順

- プリフロップ: UTG → HJ → CO → BTN → SB → BB
- ポストフロップ: SB → BB → UTG → HJ → CO → BTN

### 6.2 初期状態

- 全員からアンティを徴収してポットに入れる（スタック不足時は全額）。アンティでスタックが 0 になった席はオールイン扱い。
- SB と BB がブラインドをポスト（スタック不足時は全額でオールイン）。
- プリフロップの現在ベット額は BB、最小レイズ幅は BB。
- 状態として「最後の有効なレイズ以降にアクション済みの席」を持つ（6.3 の再オープン判定に使う）。

### 6.3 合法アクション

| 状況 | 取れるアクション |
|---|---|
| to call > 0 | フォールド、コール（min(to call, スタック)）、レイズ（レイズ可能条件を満たす場合） |
| to call = 0 かつ現在ベット額 = 0 | チェック、ベット（スタック > 0 かつ、アクション可能な他の席がいる場合） |
| to call = 0 かつ現在ベット額 > 0（BB オプションなど） | チェック、レイズ（レイズ可能条件を満たす場合）。表示・保存ともに「レイズ」として扱い、% pot はレイズ式（6.6）で計算する |

- レイズ可能条件: スタック > to call、かつアクション可能な他の席がいる、かつ「最後の有効なレイズ以降に自分がアクションしていない」。
- 最小レイズ to = 現在ベット額 + 直前の有効なレイズ幅。ただし残りスタックが足りない場合はオールインまで。
- 最小ベット = BB（スタック不足時は全額）。
- 最大 = 現在ベット額 + 残りスタック（オールイン）。
- 有効なレイズ: レイズ幅が最小レイズ幅以上のもの。有効なレイズがあると最小レイズ幅を更新し、「最後の有効なレイズ以降にアクション済みの席」を空にする（アクションが再オープンされる）。
- 不完全レイズ（最小レイズ幅に満たないオールイン）: 現在ベット額は更新するが、最小レイズ幅は更新せず、アクションも再オープンしない。すでにアクション済みの席は、追加分に対してコールかフォールドのみ取れる。

### 6.4 ストリートの終了とハンドの終了

- 次にアクションする席: 直前にアクションした席の次から順に、フォールドしておらず、オールインでもなく、「このストリートで未アクション」または「現在ベット額に届いていない」最初の席。
- 該当者がいなければストリート終了。ベットをポットに集め、次のストリートへ進む。
- 残り 1 人になったらハンド終了（ポット獲得）。
- アクション可能な席が 1 人以下でベット額が揃っている場合は、ランアウト（ボード 5 枚入力）を経てショーダウン。
- リバー終了時はショーダウン。

### 6.5 スポットの判定

- 5.2.7 の通り。回答時の合法アクションは、停止位置の状態で Villain について 6.3 を適用する。
- 回答画面のアクションのキーは次のいずれかの組み合わせになる: `fold, call, s1` / `fold, call`（レイズ不可）/ `check, s1` / `check`（ベット・レイズ不可）。`s1` の表示名は、現在ベット額 = 0 なら「ベット」、それ以外は「レイズ」。

### 6.6 % pot の計算

- ポット基準 = 回収済みポット + 全員の現在ベット額 + Villain のコール額（コール後のポット。Villain のコール額はスタック不足なら全額）
- ベット（現在ベット額 = 0）: サイズ = ポット基準 × p
- レイズ（現在ベット額 > 0。to call = 0 の BB オプションを含む）: レイズ to = 現在ベット額 + ポット基準 × p
- 結果は min〜max に丸める。
- 例 1: ポット 9.1bb、BTN が 6.5bb ベット、BB が回答 → ポット基準 = 9.1 + 6.5 + 6.5 = 22.1、50% = 6.5 + 11.05 = 17.55bb
- 例 2: リンプ 2 人と SB コンプリートで BB がオプション（ポット基準 = 4bb、現在ベット額 1bb）→ 50% = 1 + 2 = 3bb。最小レイズ to = 2bb

### 6.7 未対応

- サイドポットの計算（マルチウェイのオールインで額が異なるケース）。ポット表示は合算のみ。
- レーキのポットからの控除（値は保存するが計算には使わない）。
- ICM 情報（スコープ外）。

## 7. データモデル

保存先は Supabase（Postgres）。表と RLS、トリガで構成する。以下は論理形式であり、列の型は実装側で決める。

### 7.1 posts（スポットの要約。一覧に使う）

```json
{
  "id": "uuid",
  "author_uid": "string",
  "created_at": "timestamp",
  "title": "string (<= 40)",
  "fmt": "cash | mtt",
  "hero": "BTN",
  "villain": "BB",
  "street": "pf | flop | turn | river",
  "effective_stack": 100,
  "keys": ["fold", "call", "s1"],
  "s1_label": "raise | bet",
  "min_to": 17.55,
  "max_to": 100,
  "pot_base": 22.1,
  "answer_count": 37
}
```

- `street` 以降の派生メタは投稿時にサーバー側で 6 章のロジックを再生して確定する（5.2.8）。
- `answer_count` はトリガでのみ更新する。

### 7.2 post_hands（ハンド本体。回答・集計画面で読む）

```json
{
  "post_id": "uuid",
  "sb": 0.5,
  "bb": 1,
  "ante": 0,
  "rake": 5,
  "stacks": { "UTG": 100, "HJ": 100, "CO": 100, "BTN": 100, "SB": 100, "BB": 100 },
  "hero_cards": ["Ad", "Kd"],
  "board": ["Kh", "8d", "3c", "2s", "7h"],
  "actions": [
    { "street": "pf", "pos": "BTN", "type": "raise", "to": 2.5 },
    { "street": "pf", "pos": "BB", "type": "call" }
  ],
  "spot_index": 10,
  "known_cards": { "BB": ["Ks", "Js"], "CO": "muck" },
  "host_answer": { "paint": "…", "size": 17.55 }
}
```

- カード表記: ランク `AKQJT98765432` + スート `s h d c`。
- `type`: `fold | check | call | bet | raise`。`to` は bet / raise のみ、そのストリートでの合計額。BB オプションのレイズは `raise`。
- `known_cards`: Hero 以外で、ハンドが判明している席はカード（フォールド後に見せた席を含む）、ショーダウンに残って未判明の席は `"muck"`。
- `hero_cards` と `known_cards` は、回答済みのユーザーと投稿者にだけ返す（7.6）。
- プレイヤー名は保存しない（ポジションのみ）。

### 7.3 answers（回答）

```json
{
  "post_id": "uuid",
  "uid": "string",
  "created_at": "timestamp",
  "paint": "169 マス × 4 バイト（fold, check, call, s1 の順。各 0〜20）",
  "size": 17.55
}
```

- 主キーは `(post_id, uid)`。1 ユーザー 1 スポット 1 件を構造で保証する。
- `paint` は 169 マス分の固定長バイト列（676 バイト）。マスの順序は 13×13 の行優先（AA, AKs, …, A2s, AKo, KK, …）。4 バイトの合計が 0 のマスはレンジ外、それ以外は合計 20。
- 合法でないキーの位置は必ず 0。
- `size` はベット・レイズの to（bb、数値）。`s1` を使っていない回答では null。
- 挿入のみ。更新・削除は投稿削除とアカウント削除のカスケードだけ（5.3.8, 5.5）。

### 7.4 post_aggregates（集計。トリガで維持）

```json
{
  "post_id": "uuid",
  "n": 37,
  "cells": "169 マス × (レンジ内人数 2 バイト + 各アクションの合計頻度 4 × 2 バイト)"
}
```

- 各アクションの合計頻度は 5% 単位の整数の和（20 = 1 人が 100%）。平均頻度 = 合計 ÷ (レンジ内人数 × 20)。
- `answers` への挿入トリガで差分加算する。削除は投稿削除のカスケードのみなので減算は不要（アカウント削除時は該当行を減算する。7.6）。
- 容量: 1 行約 2KB。

### 7.5 容量の見積もり

- 100 人、1 人月 10 投稿、1 投稿平均 30 回答の場合: posts + post_hands で月約 3MB、answers 約 0.7KB × 30,000 = 月約 21MB、post_aggregates 月約 2MB。
- Supabase 無料枠（500MB）で 1 年半程度。容量 70% で 8 章の整理ルールを発動する。

### 7.6 権限とサーバー側処理（RLS とトリガ）

| 対象 | ルール |
|---|---|
| すべての表 | 未認証は読み書き不可 |
| posts | 認証済みは全件読める。挿入は本人のみ、投稿上限（1 日 5 件）をトリガで検査。更新不可。削除は本人と管理者 |
| post_hands | 読み取りは認証済み全員。ただし `hero_cards` と `known_cards` は、投稿者本人か、その post に自分の回答がある場合のみ返す（ビューまたは RPC で分離）。`host_answer` の更新は投稿者のみ |
| answers | 挿入は本人のみ、投稿者本人は不可、既存行があれば不可（主キー）。トリガで 5.3.8 の検証（マスの合計 20、合法キー以外は 0、size の範囲）。読み取りは自分の行のみ |
| post_aggregates | 読み取りは、その post に自分の回答がある場合と投稿者本人のみ。書き込みはトリガのみ |
| 投稿削除 | posts の削除で post_hands、answers、post_aggregates を外部キーのカスケードで削除 |
| アカウント削除 | RPC で、本人の posts（カスケード）と answers を削除し、answers の削除ごとに post_aggregates を減算、`answer_count` を減算。最後に認証ユーザーを削除 |
| 管理者 | 管理者 UID の一覧を DB の設定表に持ち、RLS から参照する |

## 8. 非機能要件

| 項目 | 方針 |
|---|---|
| コスト | サーバー代ゼロ。Supabase 無料枠（Auth の Google プロバイダ、Postgres、RLS、トリガ）。静的ホスティングは無料枠のあるサービスを使う（候補の選定は実装側） |

| 容量 | 7.5 の見積もり。使用量が 70% に達したら、回答数 0 の古い投稿から順に削除する整理ルールを発動する（管理者が実行） |

| プライバシー | プレイヤー名を保存・表示しない。Google の表示名とメールアドレスを他ユーザーに表示せず、DB にも保存しない。プライバシーポリシーに「保存するデータ（UID、ハンドヒストリー、回答）」「画像を保存・送信しないこと」「アカウント削除の方法」を記載する |
| 規約 | T4 利用規約を確認済み。本アプリはプレイ中の支援・自動収集・自動操作に該当しないと判断。アプリ側の利用規約に「対局中の使用禁止」「不適切な投稿は管理者が削除できる」を明記する |
| アクセシビリティ | ボタン・入力欄は実要素、44px 以上のタッチ領域（レンジ表のマスを除く）、キーボード操作、フォーカス表示、配色は明度差でも区別できること |
| モーション | 視差効果を減らす設定に従う |

## 10. 画面ごとのインフォメーション内容

### 10.1 一覧

- タブ: 「すべて」と「自分の投稿」。
- フィルタ: スポットのストリート（プリフロップ〜リバー）で絞り込み、新着順または回答数順に並び替え。
- 遷移: 未回答のスポットは回答画面へ、回答済みと自分の投稿は集計画面へ。他人の投稿の集計は回答するまで見られない。

### 10.2 レンジ入力

- 視点: Villain（あなた）の席から、Hero のアクションに対する Villain のレンジを入力する。
- リプレイ: スポットまでのアクションを再生する。Hero のハンドは回答後に公開される。
- ブラシ: 上部のアクションを押すとそのアクション 100% のブラシになる。バーの境界をドラッグすると混合戦略（5% 刻み）を作れる。マスをタップ、またはなぞるとブラシの頻度で塗られる。
- スポイト: マスを長押しすると、そのマスの頻度をブラシに読み込む。
- レンジ外: 塗らないマスはレンジ外（このスポットに到達しないハンド）。消しゴムで塗ったマスをレンジ外に戻せる。ブラシと同じ頻度のマスをもう一度押しても消える。
- 元に戻す・やり直す・クリア: 塗る操作を 1 回ずつ戻せる。なぞった操作は 1 回分として扱う。クリアで全マスをレンジ外に戻す。
- サイズ: 33%・50%・75%・125% はコール後のポットに対する割合。レイズの場合は現在のベット額にその分を足した額が to になる。入力欄とゲージで任意のサイズに調整できる。
- 下部のバー: 1326 combos に対する各アクションとレンジ外の比率。
- 送信: 回答は 1 スポットにつき 1 回で、送信後は変更できない。自分の投稿への入力は Hero の予想として保存され、全体の集計には含まれない。Hero の予想は何度でも変更できる。

### 10.3 集計

- 色: マス内の色の割合がアクション頻度を表す（そのハンドをレンジ内とした回答者の平均）。
- 濃さ: そのハンドをレンジ内に含めた回答者の割合。薄いほどレンジ外とした回答者が多い。
- 白枠: Villain の実際のハンド。ショーダウンがない、またはマックの場合は表示されない。
- 上部のバー: 1326 combos に対する各アクションとレンジ外の比率。レンジ内とした回答者の割合で重み付けしている。
- タブ: 全体・自分・Hero の予想を切り替えられる。マスを選ぶと内訳が表示される。
- ハンドヒストリー: ハンドを最後まで再生し、ショーダウンのハンドを確認できる。

### 10.4 スポット投稿

- 画像読み込み: T4 のハンドヒストリー画像を端末内で OCR する。画像は読み取り後に削除され、保存も送信もされない。
- 基本設定: キャッシュゲームではアンティとレーキを任意で入力する。MTT ではレーキは入力できない。アクション入力後は変更できない。
- プレイヤーとハンド: 分かっているハンドのみ入力する。Hero のハンドは必須。フォールドした席でも判明していれば入力できる。ハンド欄を押すとカードキーボードが表示される。
- カードキーボード: A キーはタップで A、押したまま上で K・右で Q・下で J・左で T。♠ キーはタップで ♠、上で ♥・右で ♦・下で ♣。1 → 0 で T。C で席のハンドをクリア、⌫ で 1 文字削除。使用済みのカードは入力できない。
- ショーダウン: ハンドが入力されていない席はマックとして扱う。
- アクション入力: そのスポットで取れないアクションは非活性になる。ストリートが終わるとボード入力に進む。「1つ戻す」はアクションだけを戻し、ボードは残る。
- スポット: Hero のアクションを 1 つと Villain を 1 つ選ぶ。回答対象はその後の Villain の最初のアクション。フォールドした席も Villain に選べる。

### 10.5 アカウント

- 利用規約、プライバシーポリシー、ログアウト、アカウント削除（投稿・回答をすべて消す。元に戻せない）。

## 11. 決定事項の経緯（抜粋）

- ランダムに手札を配って答えさせる方式は、到達しないハンド（トラッシュハンド）が混ざるため不採用。レンジを塗る方式に一本化した。
- 当初は 1 マス 1 アクションで、混合戦略は集計で表す方針だったが、レンジ入力でミックスを直接設定できる方式に変更した。
- 「ここまで来ない」は独立した色ではなく、塗らないマス（レンジ外）で表す。
- レイズサイズは 2 種類から 1 種類に変更した。
- v0.2: 回答の上書きを廃止した。集計を見たあとの答え直しは多数派に寄り、アンケートとしての意味が薄れるため。副次的に集計の差分更新が加算のみになる。
- v0.2: ミックスの刻みは 5% を維持した。保存は 0〜20 の 1 バイトで容量は変わらず、集計は平均なので粒度が見やすさを損なわない。
- v0.2: 保存先は Supabase とした。回答の検証・集計・カスケード削除・投稿上限をトリガと RLS でサーバー側に置け、読み取り回数の課金がないため。Firebase は集計を Functions で行うのに Blaze プランが要り、一覧の読み取り課金が効く。
- v0.2: 回答対象は「Hero が指定した 1 スポットの Villain の 1 アクション」に限定した。Villain の候補にはフォールドした席も含める（Hero が指定する）。
