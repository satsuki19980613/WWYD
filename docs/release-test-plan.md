### D. モンキーテスト（T-D。Playwright）

**でたらめな操作を大量に行い、アプリが壊れないこと**を確かめる。種（seed）を決めた擬似乱数で操作を選び、落ちたら同じ種で再現できるようにする。

- **対象**: 一覧・投稿（手入力・下書き・画像読み込みの確認画面）・回答・集計・下書き・規約・アカウントメニュー・ⓘ。PC（1280×900・1024×640）とスマホ（Pixel 7）。偽のバックエンド（回答前・回答後・自分の投稿・エラーを返す応答も混ぜる）。
- **操作**: 見えていて押せる要素をランダムに押す（ダブルクリック・連打も）、ランダムなキー（矢印・Enter・Esc・Tab・Backspace・Ctrl+Z/Y・文字）、入力欄にランダムな文字（空・空白だけ・絵文字・結合文字・右から左の文字・`<script>`・1 万文字・数字でない値・負の数）、表のマスのドラッグ、長押し、画面の大きさの変更、ブラウザの戻る・進む・再読み込み、通信の遅延と失敗（`route` で 500・タイムアウト）。
- **毎手の点検（落ちたら種と手数を記録）**: `pageerror`（捕まえていない例外）と `console.error` が無い／画面が真っ白でない／PC の投稿・回答・集計でページがスクロールしない（FitStage）／スマホで横にはみ出さない／「undefined」「NaN」「[object Object]」が画面に出ない／Esc でモーダルが閉じる／投稿の下書きが常に再生できる（B-06 と同じ性質）。
- **量**: 画面ごとに 1 種 200 手 × 20 種（PC・スマホそれぞれ）。落ちた種は `docs/release-test/monkey-seeds.md` に残し、直したあと同じ種で再実行する。
- **合法手のランダムウォーク**（投稿専用）: 台のボタンだけをランダムに押してハンドを最後まで入れ、Spot を選んで投稿する（偽のバックエンドで本文を受け取り、B-02 と同じくサーバーの判定を通るか確かめる）。500 ハンド。

### G. 互換性と実機（さつき＋指揮役）

- Playwright で Chromium・WebKit・Firefox（1-8 の承認があれば）に E2E を回す。
- **さつきの実機**: iPhone の Safari、ホーム画面に追加したアプリ、PC の Chrome（と Edge）。確認表（`docs/release-test/device-checklist.md` を指揮役が作る）: ログイン、**再読み込み・アプリを閉じて開き直してもログインが続く**（中継。12 章 §7.2）、手入力の投稿、画像の読み込み、回答、集計、下書き、ログアウト。
- Cloudflare Pages の枝のプレビューでは Neon の trusted domains に無いためログインできない。**実機の確認は本番に反映したあと**（H）に行う。

### H. 本番に反映したあとのスモークテスト（さつきの承認の後）

1. push → PR → マージ → Cloudflare Pages の配備（Pages Functions を含む）を確かめる。
2. 本番で 1 回ログインし直す（中継に切り替わるため）。再読み込みしてもログインが続く。
3. 試験の投稿を 1 件（題名「試験」）→ 回答 → 集計 → 削除。CSP の違反が 0 件。
4. `wwyd.pages.dev/api/auth/ok` が 200、許可していない `/api/auth/*` が 404。
5. 翌日以降、さつきがログインが続いていることを確かめる（数日使わなかった場合も）。

## 6. 指摘の形と重大度

指摘は `docs/release-test/findings.md` に 1 件 1 行の表でまとめる（指揮役）。各サブエージェントの報告もこの形で出させる。

| 項目 | 内容 |
|---|---|
| ID | `F-001` から通し番号（指揮役が付ける） |
| 出どころ | 試験の ID（A-03 など）かレビュー（R1〜R3） |
| 重大度 | **S1**: 情報の漏れ・不変条件の違反・主要な流れで落ちる・データが消える／**S2**: 機能が正しく動かない（回り道はある）／**S3**: 軽い不具合・見た目の崩れ／**S4**: 改善の提案 |
| 場所 | `ファイル:行` または画面と操作 |
| 再現の手順 | 入力・操作・種（モンキー）→ 起きたこと・期待したこと |
| 状態 | 未確認 → 確認済み → 修正済み（コミット）→ 再試験済み／見送り（さつきの判断） |

- **S1・S2 は直す**（先に再現の試験を書いてから直す。CLAUDE.md §6）。S3 はまとめて直すか見送るかを指揮役が案を出し、さつきが決める。S4 は plan.md のタスクに回す。
- 仕様の解釈が分かれるものは、推測で直さず plan.md の「確認待ち」に入れてさつきに聞く。

## 7. 進め方（順番）

| 段 | 内容 | 並列 |
|---|---|---|
| 0 | §1 の準備（RC1 の固定、`E2E_PORT`、基準の実行、dev のデータ、さつきのログイン） | — |
| 1 | T-A〜T-F（Sonnet × 6）と R2・R3（Opus × 2）を**同じメッセージで**起動。指揮役は R1 と C-08・F-03 を内蔵のブラウザで行う | 8 体＋指揮役 |
| 2 | 報告を集め、重複をまとめ、1 件ずつ再現して重大度を決める（findings.md） | 指揮役 |
| 3 | S1・S2 を直す（再現の試験 → 修正 → RC2）。直した所に関わる担当に再試験を頼む（同じエージェントに SendMessage）。モンキーは落ちた種で再実行 | 必要なだけ |
| 4 | 全部の自動の試験をもう一度（関門 2・3）。サブエージェントが書いた試験で残すものを `e2e/`・`db/tests/` に移す | 指揮役 |
| 5 | `docs/release-test/report.md`（結果・件数・指摘・見送り・残った危険）と plan.md を更新し、さつきに報告。**公開の判断はさつき** | 指揮役 |
| 6 | さつきの承認 → push・PR・マージ・配備 → §3 H の本番のスモーク → §3 G の実機の確認 | さつき＋指揮役 |

- 各サブエージェントの時間の目安は 1 体あたり 1〜2 時間相当。途中で止まったら、指揮役が SendMessage で続きを頼む（新しく起動し直さない）。
- 指揮役は、サブエージェントの報告をそのまま信じない。「通った」「問題なし」は、指揮役が試験の出力か再現で確かめてから記録する。

## 8. 報告書（report.md）の目次

1. 対象の版（RC のハッシュ）と環境
2. 自動の試験の件数と結果（基準と最終）
3. 観点 A〜H ごとの結果（行ったこと・件数・合否・試せなかったこと）
4. モンキーテストの量（種の数・手数）と見つけたもの
5. レビュー R1〜R3 の要約
6. 指摘の一覧（重大度別・状態別）
7. 不変条件の対応表（§5 を埋めたもの）
8. 見送ったものと理由、残った危険
9. 公開してよいかの判断材料（指揮役の推奨）

## 9. さつきに確認・依頼すること（まとめ）

- 本番へのマイグレーションの適用（1-1）、dev へのログイン（1-7）、WebKit・Firefox のダウンロード（1-8）。
- S3 の直す・見送るの判断、仕様の解釈が分かれる指摘の判断。
- 公開（push・マージ・配備）の承認、本番のスモークでのログイン、実機の確認（G・H）。
