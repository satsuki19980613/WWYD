## A. 着手前に必要

### Q-1 ライト / ダークテーマ（矛盾）— 優先度 A
- 仕様書 §4.1「ライト / ダークテーマの両方に対応する」。一方、今回の指示「ICMCLEC の UI コンセプトを完全に踏襲」では、ICMCLEC は**ダーク固定**（Cyberpunk 2077 調の黒い HUD）。
- 選択肢:
  1. **ダーク固定**（ICMCLEC と同じ）。仕様書 §4.1 からの変更として決定ログに記録する。
  2. ICMCLEC のトークンを基にライトテーマを新たに作り、両対応にする（世界観が崩れやすく、ICMCLEC に前例がない）。
- **推奨: 1**。理由: 「完全に踏襲」の指示と一致し、黄 / シアンのネオン配色はライト地では可読性が落ちる。

### Q-2 アクションの配色と明度差（ICMCLEC 踏襲で新たに必要）— 優先度 A
- 仕様書はアクション色を定めていない（モックは fold 灰・check 緑・call 青・bet 橙）。ICMCLEC の三色規則（黄 = ブランド・アクティブ・PUSH、赤 = FOLD・損失・エラー、シアン = 情報・操作）に当てはめる必要がある。
- 仕様書 §8 アクセシビリティ「配色は明度差でも区別できること」: 黄（#fcee0a）とシアン（#3ae6ff）は明度が近い（コントラスト比 約 1.2）。
- 選択肢:
  1. **fold = 赤、check / call = シアン、bet / raise = 黄**（check と call は同じスポットに同時に出ないので同色にできる）。明度差の不足は「並び順の固定（fold → check → call → s1）」「マス内の区切り線」「凡例の数値」で補う。
  2. 1 に加え、s1 の区間に細い斜線（ハザードストライプ）を重ねて形でも区別する。
  3. レンジ表専用にシアンを暗くした派生色（例 `--cyan-deep`）を追加する（新しい色を増やす）。
- **推奨: 2**。理由: トークンを増やさず（ICMCLEC と同名のまま）、ハザードストライプは ICMCLEC のシグネチャー要素でもあり、明度に頼らない区別になる。

### Q-3 モックの版（資料の食い違い）— 優先度 A
- 依頼文では「モック（v0.2 準拠）」だが、受け取った `spot-app-prototype.html` は仕様書 §9.2 に列挙された **v0.1 の挙動**のまま（回答の上書き可、一覧のフィルタにプリフロップなし、席ラベル「Villain」、1 → スートで A、説明トーストあり 等）。仕様書 §0 でも「v0.1 時点のもの」と明記されている。
- 選択肢: 1. このファイルを正として進める（差分は仕様書 §9 のとおり仕様書を優先）。 2. v0.2 準拠の別のモックがあるなら差し替える。
- **推奨: 1**（別版があれば教えてほしい）。どちらにしても見た目は ICMCLEC 踏襲なので、モックから採るのは画面構成と操作だけ。

### Q-4 BB の入力 — 優先度 A
- 仕様書 §5.2.3「SB / BB：bb 単位で入力」。bb 単位なら BB は定義上つねに 1 で、入力の意味がない（モックは BB も編集できる）。
- 選択肢: 1. **BB は 1 固定（表示のみ）、SB だけ入力**（0 < SB ≤ 1）。 2. BB も入力可（BB ≠ 1 を許すと「bb 単位」と矛盾し、% pot・実効スタックの意味が崩れる）。
- **推奨: 1**。

### Q-5 金額の精度と丸め — 優先度 A
- 仕様書に精度の定めがない。MTT のアンティ 0.125bb（モックの見本）のように小数第 3 位が現れ、ポット・% pot の計算で端数が出る（例: 8.725bb）。サイズ入力は「0.1 刻み」（§5.3.6）。
- 推奨案（04 章 §1・§9 に記載）:
  - 内部はミリ bb の整数で計算（浮動小数の誤差を排除）。入力は小数第 3 位まで。
  - % pot から求めたサイズは **0.01bb に四捨五入**してから min〜max に収める（仕様書の例 17.55bb と整合）。
  - 入力欄の「0.1 刻み」は増減ボタンの刻みとし、直接入力は小数第 3 位まで受け付ける。
- 選択肢: 1. **推奨案**。 2. すべて 0.01bb 単位（アンティ 0.125 が入力できない）。 3. すべて 0.1bb 単位。
- **推奨: 1**。

### Q-6 実効スタックの定義 — 優先度 A
- 仕様書 §2「Hero と Villain のスタックの小さいほう（スポット時点）」。一方 §7.1 の例ではターンのスポットで `effective_stack: 100`（開始スタック 100bb のハンド。スポット時点の残りは約 96bb）。
- 選択肢: 1. **ハンド開始時のスタックの小さいほう**（例と一致。「100bb エフェクティブ」という慣用に合う）。 2. スポット時点の残りスタックの小さいほう。
- **推奨: 1**。一覧のカードに出す値なので、ゲームの深さを表す慣用に合わせる。

### Q-7 レイズの最大額の解釈 — 優先度 A
- 仕様書 §6.3「最大 = 現在ベット額 + 残りスタック（オールイン）」。「現在ベット額」を卓の現在ベット額と読むと、すでにそのストリートに出している額が大きく違う場合に誤る（例: 自分 2bb 出して残り 50bb、卓の現在ベット額 10bb → 60bb になるが、実際のオールインは 52bb）。
- 選択肢: 1. **「その席がそのストリートに出している額 + 残りスタック」と解釈**（= 正しいオールイン額）。 2. 文字どおり。
- **推奨: 1**（誤記とみなす）。

### Q-8 不完全レイズの累積 — 優先度 A
- 仕様書 §6.3 は「不完全レイズはアクションを再オープンしない」。ルールブックによっては、短いオールインが複数重なって合計が最小レイズ幅以上になると再オープンする扱いもある。
- 選択肢: 1. **仕様書の文言どおり、累積しても再オープンしない**（テスト INC-03）。 2. 累積で再オープンする。
- **推奨: 1**（まれなケースで、仕様書の文言に従う）。

### Q-9 未回答者へのハンド本体の返却（抜け道）— 優先度 A
- 仕様書 §7.6 では post_hands は「認証済み全員が読める（hero_cards と known_cards を除く）」。しかし post_hands の `actions` にはスポットより後のアクション（**Villain の実際のアクション＝答え**）が、`board` には後のストリートのカードが入っている。API を直接呼べば回答前に答えを見られる。
- 選択肢:
  1. **未回答者には、停止位置より前のアクションと、スポットのストリートまでのボードだけを返す**（`get_post_detail` で切り詰め、post_hands の直接の select は許可しない。02 章 §4.3）。
  2. 仕様書どおり全件返す（画面で隠すだけ）。
- **推奨: 1**。仕様書の意図（集計を回答前に見せない、答え直しを防ぐ）に沿う。

### Q-10 投稿上限と削除 — 優先度 A
- 仕様書 §5.2.8「投稿者のその日（UTC）の投稿数が上限（5 件）未満」。投稿して削除すれば枠が戻るのか定めがない。
- 選択肢: 1. **削除しても枠は戻らない**（日ごとの投稿回数を別の表で数える。01 章 `post_quota`）。 2. 残っている投稿の数で数える（削除すれば再投稿できる）。
- **推奨: 1**（上限の目的＝荒らし・容量対策に沿う）。

### Q-16 技術選定と依存ライブラリ — 優先度 A
- CLAUDE.md §3 の「提案・未確定」項目の承認。依存の追加は承認が必要なため、基盤フェーズで入れる予定のものを列挙する。
- 提案: React 18、React DOM、Vite、@vitejs/plugin-react、TypeScript、Vitest、@supabase/supabase-js、Supabase CLI（`supabase`、開発用）、Playwright（E2E、開発用）。ルーティングは自前の小さな実装（依存を増やさない）。スキーマ検証は自前（`packages/core` は依存ゼロ）。
- OCR フェーズで追加予定: tesseract.js（Q-17 で (a) を採る場合）。
- **推奨: 上記で承認**。ICMCLEC と同じ構成で、さつきの環境に既にある。

## B. 該当フェーズの前までに必要

### Q-11 Google の表示名の認証基盤側での保持 — 優先度 B（DB と認証フェーズ）
- 仕様書 §8「Google の表示名とメールアドレスを他ユーザーに表示せず、DB にも保存しない」。§3 ではメールアドレスは「認証基盤側の保持のみ」可。Supabase Auth は Google から受け取った表示名・プロフィール画像 URL も `auth.users.raw_user_meta_data` に保存する（ログインのたびに更新）。
- 選択肢:
  1. **メールアドレスと同じく「認証基盤側の保持」として許容**し、アプリの表（public スキーマ）には一切写さない。プライバシーポリシーに明記。
  2. `auth.users` のトリガで表示名・画像 URL を消す（Supabase 内部の表への介入で、将来の仕様変更で壊れるおそれ）。
- **推奨: 1**。

### Q-12 Supabase の休止対策 — 優先度 B（リリース前）
- 仕様書 §8 は「管理者が手動で再開、停止中はメンテナンス表示」。GitHub Actions の定期実行（無料）で週数回アクセスすれば停止を防げる（ICMCLEC の warm-ping と同じ）。
- 選択肢: 1. 仕様書どおり手動再開。 2. **定期アクセスで停止を防ぐ**（メンテナンス表示は保険として残す）。
- **推奨: 2**（利用者が「メンテナンス中」に当たる機会を減らせる）。仕様書からの変更になるため判断を仰ぐ。

### Q-13 ログイン画面 — 優先度 B

### Q-14 Hero の予想入力時の Hero のハンド表示 — 優先度 B

### Q-24 RAISE-08 の期待値と §5 の規則の食い違い — 優先度 B（P2 で発見）
- 04 章 §10.3 RAISE-08（BB 3.1bb、フロップで BB が 0.6 のオールインベット）は、BTN の合法アクションを「fold, call 0.6, raise[1.6, 97.5]」としている。
- 一方 §5 の表は raise の条件に「他にアクションできる席がある（othersCanAct）」を含み、LEGAL-04 もその規則で「raise なし」としている。RAISE-08 では BB がオールイン・他は全員フォールド済みなので、規則どおりなら **BTN に raise は無い**（fold, call 0.6 のみ）。
- 選択肢: (a) §5 の規則どおり raise なしとし、RAISE-08 の期待値を直す。最小レイズ幅が変わらないことは、3 人目が残る形（RAISE-08b: `UTG..HJ f, CO r2.5, BTN c, SB f, BB c`、フロップ `BB b0.6` → CO raise[1.6, 97.5]）で確かめる。(b) オールインの相手しかいなくても raise を許す（§5 と LEGAL-04 を直す）。
- **推奨: (a)**。相手が全員オールインのときのレイズは意味がなく、仕様書 §6.3 の考え方（アクション可能な席がなければランアウト）とも合う。**2026-09-27、推奨案 (a) で決定**（04 章 RAISE-08 を修正し、RAISE-08b を追加）。
